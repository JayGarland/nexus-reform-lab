# L-0666 QUERY: Secretary Has No Reply Privilege in Its Own Dispatched Topics

## Context Digest

- Boss reported (this conversation, 2026-07-27): in a Secretary-dispatched letter Topic (example: letter-L-0664), a bare Telegram message (no `@`, no explicit Reply) is answered by Secretary — even when Boss intends it for the `To:`-bound target seat only. Boss confirmed via controlled test: bare send, no Reply tapped, no `@` used.
- Boss's own root-cause diagnosis and fix requirement (verbatim, this conversation): the Topic Secretary created/bound via its `[DISPATCH]` block causes cc-connect to implicitly treat Secretary as that Topic's "default primary responder." The correct rule: Secretary holds no special reply privilege anywhere, including Topics it dispatched — it wakes on explicit `@secretary_resonova_bot` mention or explicit Reply-to only, identically to every other seat. On a bare send with neither, only the `To:`-bound target seat should process the message; Secretary must stay observe-only.
- Code read (this letter's own investigation, `platform/telegram/telegram.go:1339-1401`, `isDirectedAtBot`): a message counts as "directed at this bot" if (a) it's a bare `/command`, (b) an entity `@mention`s this bot's username, or (c) `msg.ReplyToMessage.From.ID == self.ID`. `group_reply_all` is unset (false) for every seat in `config.toml`, confirmed by full-file grep — no seat has an explicit always-reply override.
- **Working hypothesis, not yet independently confirmed by raw Telegram payload inspection** (Evidence Gap, see below): Telegram Forum Topics implicitly link every message's `reply_to_message` to the Topic's opening/root message (whose ID equals `MessageThreadID`) as a structural artifact of how Topics are implemented, independent of whether the user tapped "Reply." Because Secretary's engine is the one that calls `CreateTaskTopic`/posts the `[DISPATCH]` intake text — i.e. Secretary's bot posts the Topic's root message — path (c) above silently fires for every subsequent bare message in that Topic, misreading Telegram's structural reply-link as a deliberate reply to Secretary.
- Archive scan (L-0636): grepped `INDEX.md` for `isDirectedAtBot`/reply_to_message/mention+topic/唤醒 — no letter previously diagnosed this exact defect. Related but distinct prior art: L-0439 (`reply_to_message` deliberately preserved for **content enrichment**, i.e. quoting text into agent context — a different code path, not the reply-gating decision here) and L-0255 (Topic isolation via `chatID+topicID+userID` session keys is deliberate design — unrelated to this reply-gating question). No duplicate found.

## Query

1. Confirm (or refute, with evidence) the working hypothesis above using a real captured Telegram update from a reproducible bare-send in a dispatched Topic, not code reading alone.
2. Fix `isDirectedAtBot` so a reply-to-the-Topic's-own-root-message is never treated as "directed at me" for the seat that happens to have posted that root message — this must be a **generic** fix in the shared function (no seat-specific carve-out), since any seat that creates a Topic (not just Secretary) would otherwise get the same false privilege.
3. Confirm or fix separately: does the `To:`-bound target seat (e.g. dev-pro) currently reliably receive a bare, non-mentioning, non-replying message inside its own dispatched Topic today? If the answer, once verified, is "no" — that is a second, distinct defect (the Topic's true owner has no way to be silently reachable either) and must be reported as such, not assumed fixed as a side effect of item 2.
