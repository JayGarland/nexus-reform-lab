# L-0667 RESULT: [DISPATCH] Auto-Execute Retired — Outbox Confirm Card Is the Sole Actuator

## Conclusion

Built exactly to Boss's spec. `maybeHandleDispatchBlock` no longer calls `ControlPlaneDispatch` the instant a `[DISPATCH]` block parses — it renders a confirm card (Letter/Thread/To/Path + a "[✅ Confirm Dispatch]" button) via `ReceiptCardManager` and records the request as pending. The ONLY path that actually dispatches is Boss pressing that button, which `handleCallbackQuery` captures as a typed `dispatch_confirm:<letter>` callback and hands **directly** to a new `Engine.ConfirmDispatch` method — the first callback in this codebase that does not resynthesize into a `core.Message` and re-enter the handler pipeline (every existing callback — `cmd:`, `askq:`, `perm:` — does exactly that, confirmed by re-reading the full function). This retires the third and last of L-0658's diagnosed text-actuation holes. Committed to `F:\foundry\worktrees\cc-connect-L-0660`, branch `architect/L-0660-session-transparency-ledger`, commit `38de8d79`, unpushed.

## What was built

- `core/dispatch_confirm.go`: `PendingDispatch` + `pendingDispatchStore` (same atomic-write/mutex-guarded JSON shape as `dispatchStore`), keyed by Letter ID. `takeByLetter` removes on read, making confirmation idempotent by construction — a double press or a stale letter finds nothing pending rather than dispatching twice. `Engine.ConfirmDispatch(p, letterID)` looks up the pending entry, calls `ControlPlaneDispatch` (L-0662's existing entry point, reused not duplicated — so the audit log and dispatch ledger behave identically to before), and updates the card via `ReceiptCardManager.UpdateReceiptCard` (buttons cleared).
- `core/interfaces.go`: `DispatchConfirmHandler` type + `DispatchConfirmReceiver` optional interface, deliberately mirroring `Start(handler MessageHandler)`'s existing injection shape (`core/engine.go:2560`, `p.Start(e.handleMessage)`) rather than inventing a new wiring pattern.
- `core/dispatch.go`: `configureDispatch` now also calls `wireDispatchConfirmHandlers()` (injects `e.ConfirmDispatch` into any Platform implementing the receiver interface). `maybeHandleDispatchBlock` rewritten: validates as before, then — if the source platform implements `ReceiptCardManager` — sends the confirm card and records the pending entry instead of executing; **if it does not**, falls back to the pre-L-0667 auto-execute behavior (QUERY item 5's disclosed decision, not a silent platform inconsistency).
- `platform/telegram/telegram.go`: `SetDispatchConfirmHandler` + new `dispatch_confirm:` branch in `handleCallbackQuery`, placed before the `cmd:` branch, calling the injected handler directly and editing the card only for the stale/not-found case (the success case is already handled by `ConfirmDispatch` itself via `ReceiptCardManager`).

## Evidence Gaps (L-0647)

1. **Card placement interpretation.** Boss said "复用既有 Outbox 卡片组件" (reuse the existing Outbox card component). I interpreted this as reusing the **card-rendering mechanism** (`ReceiptCardManager`, the same interface the Outbox module already uses) and posted the confirm card to the current dispatching session/topic — not as literally routing it into the Outbox's dedicated `outbox_session_key` topic, which is documented in `config.toml` as "Read-only queued QUERY cards... does not dispatch work or inject a Secretary turn" — repurposing that specific topic for an execute-triggering button would conflict with its own stated scope. If Boss meant the literal Outbox topic, this needs a follow-up adjustment; flagging the interpretation rather than assuming it's obviously correct.
2. **No mocked-bot integration test for the full Telegram round-trip beyond `handleCallbackQuery` itself.** `TestHandleCallbackQuery_DispatchConfirm{,Stale}` exercise the real `handleCallbackQuery` function against a stub bot and prove the direct-call wiring and stale-handling behavior. They do not exercise `SendReceiptCard`'s own HTML-rendering/retry logic (already covered by pre-existing tests elsewhere) in combination with this new branch. I judged this sufficient given the new branch itself is a thin dispatcher (prefix check → direct call → conditional edit), with the substantive logic covered at the `core` level — but it means the very first real button press in production is still the first time the full path runs end-to-end. This is exactly why Boss verifying live after deploy (already planned) matters here.
3. **`ConfirmDispatch`'s error path when `dispatchErr != nil`** (i.e., confirm was pressed but the underlying `executeDispatch` failed — e.g., target seat not running) updates the card to show the error and still returns `ok=true` (a pending proposal WAS found and consumed) with a non-nil `err`. This means a failed dispatch cannot be retried by pressing the same button again — the pending entry is already consumed. I did not add a "re-propose" path for this case since Boss's spec didn't ask for one; flagging it as a real gap if Boss expects a failed confirm to be retriable in place rather than requiring Secretary to re-emit a fresh `[DISPATCH]` block.
