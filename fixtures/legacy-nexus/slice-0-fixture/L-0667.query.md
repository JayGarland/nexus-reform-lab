# L-0667 QUERY: Retire [DISPATCH] Text-Implicit Trigger — Outbox Confirm-Card Replaces Auto-Execute

## Context Digest

- (L-0658) RFC diagnosed the `[DISPATCH]` block as one of three text-actuation holes: an assistant-generated text block, regex-matched, auto-executing a cross-engine relay dispatch with no confirmation step.
- (L-0662) Phase 2 wrapped the auto-execute call in `ControlPlaneDispatch`, adding an audit log — but did not remove the auto-execute itself; `maybeHandleDispatchBlock` still calls it the instant the block parses successfully.
- (this conversation) Boss reviewed the Phase 3 options (native LLM tool-calls, found to require new adapter-layer capability that doesn't exist) and chose a different, fully-specified design instead of Phase 3: replace the auto-execute with a Telegram Outbox-style confirmation card. Boss's own words (verbatim): reuse the existing Outbox card component (`ReceiptCardManager` style) to render a dispatch-proposal card with letter metadata and a "[Confirm Dispatch]" button; the button's callback must be captured by `handleCallbackQuery` and call `ControlPlane.Dispatch(DispatchIntent)` **directly** — not via the existing text-resynthesis pattern every other callback in this codebase uses.
- Code read (this letter's own investigation): `handleCallbackQuery` (`platform/telegram/telegram.go`) has exactly three callback_data prefixes today (`cmd:`, `askq:`, `perm:`) and **all three** resynthesize into `p.handler(&core.Message{Content: ...})` — none call a Go function directly. This confirms L-0658's diagnosis hole #3 (button UI collapses into free text) with zero exceptions; this letter's card is the first callback in the codebase that must NOT do that. `Platform.Start(handler MessageHandler)` (`core/interfaces.go:12`, wired at `core/engine.go:2560`, `p.Start(e.handleMessage)`) is the existing precedent for how the Engine injects a callback into a Platform — the new confirm-handler wiring mirrors this shape rather than inventing a new one.
- Archive scan (L-0636): grepped `INDEX.md` for "confirm card"/"dispatch button"/"ReceiptCardManager" — L-0449/L-0451 (one-click close-letter button) is the closest prior art but, per the code read above, is itself built on the text-resynthesis `cmd:` callback — not a precedent for a direct-call callback. No letter has built a direct-call (non-resynthesizing) callback before. No duplicate found.

## Query

1. `maybeHandleDispatchBlock` must stop calling `ControlPlaneDispatch` the instant a `[DISPATCH]` block parses and validates. Instead: validate as today (`parseDispatchBlock` + `validateDispatchArchive`, unchanged), then render a dispatch-proposal card (Letter/Thread/To/Path) with a "[✅ Confirm Dispatch]" button, and store the pending request keyed by Letter ID.
2. Add the plumbing for a direct-call callback: a new optional `Platform` interface (mirroring `Start(handler MessageHandler)`'s injection shape) that the Telegram adapter implements, wired by the Engine, so pressing the button calls an `Engine` method directly — no `p.handler`/message resynthesis anywhere in this path.
3. On confirm, look up the pending request, call `ControlPlaneDispatch` (Phase 2's existing entry point — reused, not duplicated), remove the pending entry, and edit the card in place to show the real dispatch receipt (or an error if it failed).
4. Handle the stale/double-press case (pending entry already consumed or never existed) gracefully — edit the card to say so, do not error silently or dispatch twice.

## Expected Output

1. New store for pending dispatch proposals (mirror `dispatchStore`'s atomic-write/mutex-guarded JSON shape), keyed by Letter ID, holding the `dispatchRequest`, source session/platform info, and the card's `MessageLocator` (so it can be edited in place on confirm).
2. `core/interfaces.go`: new type + optional interface for the direct-call confirm handler. `core/engine.go`: wiring at `Start()` (or `configureDispatch`) to inject it into any `Platform` that implements it. New `Engine` method that performs the lookup + `ControlPlaneDispatch` call + pending-entry cleanup.
3. `platform/telegram/telegram.go`: implement the new interface; add the `dispatch_confirm:`-prefixed branch to `handleCallbackQuery` that calls the injected handler directly and edits the card via `UpdateReceiptCard`.
4. Tests: pending-store round-trip; confirm-success path (card edited to receipt, `ControlPlaneDispatch` invoked exactly once, audit log entry present per L-0662); confirm-on-missing-pending path (graceful, no panic, no dispatch); the existing `dispatch_test.go` coverage for `parseDispatchBlock`/`validateDispatchArchive` stays green since those are unchanged.
5. If a source platform does NOT implement `ReceiptCardManager` (card rendering unsupported), state explicitly what happens (fallback to the old auto-execute vs. reject-with-message) as a disclosed design decision, not a silently platform-inconsistent behavior — this is a real open question, decide it and report the choice, don't leave it undefined.
6. `go vet`/`go build`/`go test ./core/... ./platform/telegram/...` clean. Continue on the existing `F:\foundry\worktrees\cc-connect-L-0660` worktree/branch, per Boss's stated preference — no new worktree.
