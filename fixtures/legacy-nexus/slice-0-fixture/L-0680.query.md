# L-0680: 审计派工静默拦截失效、大小写敏感漏洞与秘书自我检测反馈盲区

## Executive Summary

在 L-0679 派工过程中，发生了一起由总裁亲自发现并纠正的系统级派工静默失效事故：
1. 秘书在创建信件 FrontMatter 时，凭编程惯性写成了小写 `id: L-0679`；
2. `cc-connect` 的 `validateDispatchArchive` (`core/dispatch.go:298`) 在校验 FrontMatter 时对 `ID` 键名严格区分大小写，导致提取为空串 `ID=""` 并拒绝派工；
3. **最严重的系统盲区**：派工被拒绝后，系统未向 Telegram 前台发出显式大声告警（Silence Failure），且 Telegram `/outbox` 命令因未入账而毫无反应。若非总裁主动追问“Outbox 里为什么没有”，这次派工将被永久静默吞没。

总裁指令：写信给架构师，要求彻底审计并治治这一漏洞——明确到底是修 `cc-connect` 容错与告警、修秘书的写入纪律与写后自检，还是两者同修，确保此类“静默拦截、前台无知觉”的事故不再发生。

## Context Digest

- **`L-0465` (CLOSED)**：`/outbox` 命令逻辑重构，剔除已派工历史，仅匹配待处理 Outbox 卡片。

- **`L-0654` (CLOSED)**：修复 `cc-connect` 账本并发与更新竞态窗口。

## Findings & Root Cause Analysis

本次事故暴露出三层交叉漏洞：

### 1. `cc-connect` 校验层的过敏与容错缺失（系统侧）
- `core/dispatch.go:319` 的 `parseArchiveFrontMatter` 使用严格区分大小写的键名提取；
- 实际上 YAML/FrontMatter 在行业惯例与协议中常用大小写不敏感或不区分大小写的解析；由于 `headers["ID"]` 强查大写，导致 `id:` 被解析为 Missing ID，产生虚假拦截；
- 拦截后，`cc-connect` 仅抛出 Go error，未将失败错误以高亮告警卡片形式实时回推给发送方（Telegram/CLI），导致“静默拒绝”。

### 2. `/outbox` 看板的反馈盲区（展示侧）
- 当 `[DISPATCH]` 被拒绝时，派工既没有进入 `dispatch_expectations.json`（派工账本），也没有进入 Outbox 成功看板；
- 前台无任何状态变化，总裁与秘书均无法从界面感知到“刚才的派工被系统拒绝了”。

### 3. Secretary 写作习惯与写后不自检（秘书侧）
- 秘书在落盘 `L-0679.query.md` 时凭惯性写入小写 `id:`，违背了规范；
- 动笔写完后，未对生成的信头执行逻辑正则自验，盲目假设“写了就能成功派工”。

## Expected Output

请架构师出具根治方案并实施改动（或提出跨仓库重构 PRD）：

1. **`cc-connect` 代码层修复 (Go 侧)**：
   - 评估 `parseArchiveFrontMatter` 是否应改为大小写不敏感匹配（Case-insensitive Key Lookups，如支持 `ID`/`id`/`Id`），提升系统鲁棒性；
   - **硬性告警机制**：当 `[DISPATCH]` 校验失败（被 `validateDispatchArchive` 拦截拒绝）时，系统必须向当前 Topic/Session 发送显式失败通知卡片（例如 `⚠️ Dispatch rejected: letter header ID="" does not match L-0679`），绝不允许静默吞没。
2. **Secretary 规则与自检硬化 (Nexus 侧)**：
   - 在 Secretary 人设/规范中硬化 FrontMatter 大写规范校验（`ID:` / `Type:` / `Thread:` / `To:` / `Route:` / `Date:`）；
   - 在写信流程中增加落盘后信头正则检查点。
3. **架构师裁决**：明确责任归属与修复组合（`cc-connect` 告警 vs 秘书规范），并完成落盘与实施。
