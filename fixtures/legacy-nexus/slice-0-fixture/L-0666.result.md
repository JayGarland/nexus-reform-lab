# L-0666 RESULT: Fixed the False Topic-Root Reply Privilege — One Confirmed Fix, One Open Verification

## Conclusion

Fixed `isDirectedAtBot` (`platform/telegram/telegram.go`) so a message whose `reply_to_message` points at its own Telegram Forum Topic's root message no longer counts as "directed at" whichever bot happens to have posted that root — the mechanism that let Secretary's own `[DISPATCH]` intake message silently grant it default-responder status in every Topic it dispatches. The fix is generic (lives in the one shared function every seat's bot uses), not a Secretary-specific carve-out, matching Boss's stated rule that no seat holds special reply privilege. Committed to the existing `F:\foundry\worktrees\cc-connect-L-0660` worktree, branch `architect/L-0660-session-transparency-ledger`, commit `3d5fba7c` — no new worktree, per your stated preference. **Item 3 of the QUERY (does the target seat already reliably receive bare messages in its own dispatched topic) is not resolved — flagged below, not silently assumed.**

## What changed

`platform/telegram/telegram.go`, `isDirectedAtBot`'s reply-to-self check now excludes the case `msg.ReplyToMessage.ID == msg.MessageThreadID` (a reply pointing at the Topic's own opening/root message) before trusting `msg.ReplyToMessage.From.ID == self.ID`. A genuine reply to a **later** message from the bot (an ID different from the Topic's root) still counts — preserves the legitimate "tap reply to continue talking to this bot" UX.

## Evidence Gaps (mandatory, L-0647)

1. **QUERY item 1 (raw payload confirmation) — not obtained.** I did not capture or inspect a real Telegram update JSON for Boss's repro; the fix is based on structural reasoning about how Telegram implements Forum Topics (every message's `reply_to_message` implicitly links to the Topic's root, independent of a deliberate user Reply tap), not a confirmed captured payload. I don't currently have DEBUG-level Telegram payload logging enabled to verify this directly, and didn't want to spend a live-reproduction cycle (restart, enable debug, ask Boss to resend) without checking whether the fix already resolves the symptom in practice first. **This should be treated as a plausible, well-reasoned mechanism, not a confirmed root cause**, until Boss reports the fix actually stops the behavior in a real dispatched Topic.
2. **QUERY item 3 (target-seat bare-message reception) — genuinely unresolved, not fixed by this change.** I looked for a mechanism that lets a `workspace_pattern`/`dispatch_topic_isolation` seat (e.g. dev-pro) treat every message in its own bound Topic as directed-at-it, bypassing the mention/reply requirement — and found none. `group_reply_all` is unset (false) for every seat in `config.toml` (confirmed by full-file grep), and `isDirectedAtBot` has no topic-ownership-aware branch for any seat. On the code as it stands, a bare, non-mentioning, non-replying message in a dispatched Topic would **not** currently reach the target seat either, unless it happens to be a genuine reply to that seat's own later message. Boss's stated requirement ("确保 To: 绑定的目标工程师席位成为该 Topic 裸文本的唯一处理者") describes what *should* be true, but I could not confirm from code or logs whether it already *is* true in practice (e.g., because real usage always naturally replies-to or mentions the target seat, masking the gap) or whether it is a second, still-open defect. **I am not building a target-seat topic-ownership bypass in this letter** — that would be inventing a second, more invasive mechanism (bridging Engine-level dispatch/binding knowledge into the Platform-level reply gate) without first confirming the gap is real, which the Out-of-Scope/Evidence-Gaps discipline (L-0644/L-0647) says not to do.
