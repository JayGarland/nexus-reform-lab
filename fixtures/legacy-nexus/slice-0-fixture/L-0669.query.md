# L-0669 QUERY: Telegram Forum Topic 专属席位裸文本自动路由重构

## Context Digest

- **L-0658 (cc-connect 控制面重构 RFC)**：确立了会话控制面与数据面解耦、传感器不触发动作、唯一控制中枢的不变量。
- **L-0666 (Telegram 根节点引用特权修复)**：剥离了原 `isDirectedAtBot` 中“指向 Topic 首条根消息即自动误判为回复 Bot”的假象特权 (commit `3d5fba7c`)，移除了 Secretary 错误接管所有 Topic 的漏洞。但该修复切断假象后，暴露出了底层真实的路由断层：目标派工席位（如 `dev-pro`）在自己的 Topic 频道内目前缺少正规接收裸文本的机制（被记为 Evidence Gap 3）。
- **L-0667 (Outbox Confirm Card 派工)**：彻底废除了从正文裸文本正则匹配起线程的自由文本触发漏洞，派工必须经 Outbox 卡片显式点击确认 (commit `38de8d79`)。

【秘书注/提醒】：本信所附的分析路径与解决方案仅作为秘书层的翻译与讨论参考，非硬性指令；执行席位（`architect`）须独立应用自身专业判断，设计并落地最终的实现方案。

## Query

总裁要求在不重蹈覆辙（严禁恢复文本正则抓取、严禁恢复根节点隐式 Reply 伪特权、严禁引入新漏洞）的前提下，正规化实现 **Telegram Forum Topic 内专属席位裸文本自动接收** 机制。

请 `architect` 设计并实现：
1. **结构化 Topic 属主绑定**：当 Telegram 收到 Topic 内的裸文本（无 `/command`、无 `@mention`、无显式 Reply）时，`isDirectedAtBot` 不得通过消息文本或 Telegram 隐式 `reply_to` 猜解，而应从派工账本/绑定关系中查询：该 `TopicID` 是否显式绑定给当前 Seat。
2. **准确路由**：若 `TopicID` 归属于当前 Seat（如 `dev-pro`），则该 Seat 的 Bot 自动识别为目标接收者（`isDirectedAtBot = true`）；无关 Seat（如 `secretary`）保持静默（`isDirectedAtBot = false`）。
3. **安全边界**：确保重构符合 L-0658 架构约束，不破坏 L-0666 与 L-0667 已经落地的控制面防护。

## Expected Output

1. `cc-connect` 代码修改与单元测试，证明被派工 Seat 可在其 Topic 内直接接收裸文本，同时非属主 Bot 保持静默。
2. `go test ./core/... ./platform/telegram/...` 全量通过。
3. 预算：3 轮以内不收敛则交 STUCK。
