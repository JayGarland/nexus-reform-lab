## Conclusion

`isDirectedAtBot` (`platform/telegram/telegram.go`) now has a structured, non-heuristic fallback: a **truly bare** message (no `/command`, no `@mention` to **any** bot, no explicit reply) inside a Forum Topic is accepted only when an injected `TopicOwnershipChecker` reports that Topic's ID as bound to **this seat** — checked against two durable sources, not message content. This closes:

1. The gap L-0666's RESULT flagged and explicitly declined to build without confirmation first (Evidence Gap 2 there).
2. The follow-up gap Boss found in live use: a Topic created via an explicit `@mention` in the General topic (`handleGeneralTopicIntake`) was never registered anywhere, so its owning seat still couldn't receive bare follow-up text even after the first fix.
3. **An over-reach bug Boss found in further testing**: In a Topic already bound to seat A, if Boss @mentioned seat B instead, **both** A and B would receive and reply — now fixed by ensuring explicit signals strictly override Topic ownership.

**Binding sources**:
1. **Dispatch-ledger source** (original QUERY scope): `DispatchExpectation.To == this seat`, for Topics opened via `[DISPATCH]` — reuses `findLetterIDByTopic`'s existing match.
2. **Topic-seat-binding source** (Boss's first follow-up): a new `topic_seat_bindings.json` store, written once — deterministically, from the already-computed "which bot's own username matched this @mention" signal — the moment `handleGeneralTopicIntake` creates a Topic for itself.

**Priority rules (L-0669 second follow-up fix)**:
- If message has **any** `/command` → only the targeted bot (or all bots if no @suffix) accepts.
- If message has **any** `@mention` (to **any** bot) → only the explicitly @mentioned bot accepts; Topic ownership is **not** consulted.
- If message has **any** explicit reply (not counting Telegram's implicit Topic root reply) → only the bot being replied to accepts.
- Only **truly bare** messages with none of the above → Topic ownership fallback applies.

A `dev-pro`-bound Topic (via either path) now auto-receives Boss's bare follow-up text with no repeated `@`; an unbound Topic, or one bound to a different seat, stays silent. Crucially: if Boss changes their mind and @mentions a different seat in that same Topic later, **only the newly @mentioned seat** responds — the original Topic owner correctly stays silent. ## What changed

1. **`core/interfaces.go`** — new optional-extension pair, mirroring the existing `DispatchConfirmHandler`/`DispatchConfirmReceiver` injection shape (`p.Start(e.handleMessage)`'s pattern):
   - `TopicOwnershipChecker func(topicID string) bool`
   - `TopicOwnershipReceiver interface { SetTopicOwnershipChecker(checker TopicOwnershipChecker) }`
2. **`core/engine.go`**:
   - `Engine.Start()` wires `SetTopicOwnershipChecker(e.isTopicBoundToSeat)` into every platform implementing `TopicOwnershipReceiver`, alongside the existing `SetLifecycleHandler`/`p.Start` wiring — unconditional, not gated on `dispatchConfig.Enabled` (that flag only governs who may *emit* a `[DISPATCH]`; every seat's own engine needs to *read* the shared ledger to answer ownership for itself).
   - `Engine.isTopicBoundToSeat(topicID string) bool` — a one-line wrapper reusing `findLetterIDByTopic`'s existing `exp.To == e.name` match (`return e.findLetterIDByTopic(topicID) != ""`). No new matching logic: letter-ID resolution and Topic-ownership routing now share one code path, so they cannot disagree about who owns a Topic.
3. **`platform/telegram/telegram.go`**:
   - `Platform.topicOwnershipChecker core.TopicOwnershipChecker` field + `SetTopicOwnershipChecker` setter (same lock discipline as `dispatchConfirmHandler`).
   - `isDirectedAtBot`'s final fallback (right before the terminal `return false`, i.e. strictly after command/mention/explicit-reply/caption-mention have all been checked and none matched): if `msg.MessageThreadID != 0` and a checker is wired, call `checker(strconv.Itoa(msg.MessageThreadID))`; accept only on `true`.

**Why the checker lives on `Engine`, not a new store:** the dispatch ledger (`dispatch_expectations.json`, `core/dispatch.go`) already records `TopicID` + `To` per dispatched letter, and `findLetterIDByTopic` already filters on `exp.To == e.name` for the *target* engine — this is precisely "TopicID bound to current Seat." L-0275 (CLOSED) previously fixed a cross-engine-invisibility bug in this same ledger, confirming (and now leaned on again) that all engines in the fleet's single process share one physical ledger file via a common `dataDir` — so a Topic bound by the *source* (e.g. secretary) engine at dispatch time is correctly readable by the *target* (e.g. dev-pro) engine's own `Engine.Start()`-wired checker, with no new plumbing between engines required.

## Follow-up (2026-07-27): General-Topic-Intake Ownership Recording

**The gap Boss found:** `handleGeneralTopicIntake` (`platform/telegram/telegram.go`) creates a new Forum Topic the moment an explicit `@mention` of THIS bot's own username arrives in the General topic (threadID == 0). It dispatches that *triggering* message directly (`WasMentioned: true`, no gate needed), but never recorded the new Topic anywhere durable. So the first fix's checker had nothing to match: the new Topic never entered `dispatch_expectations.json` (it has no Letter/Path/ResultPath — it isn't a `[DISPATCH]`), and every later bare message in it fell through to `false` exactly as before.

**Why this is still deterministic, not a heuristic:** `mentioned := botName != "" && strings.Contains(msg.Text, "@"+botName)` (line ~745) already checks the mention against **this specific bot's own username**, per-engine — every seat's Telegram platform independently decides whether *it* was mentioned. `handleGeneralTopicIntake` only creates a Topic when `mentioned` is true for *this* bot. So "which seat created this Topic" was already a structured, single-valued fact at creation time; the only defect was never writing it down. No new text-scraping was introduced.

**What changed:**

4. **`core/interfaces.go`** — added the write-side counterpart to `TopicOwnershipChecker`:
   - `TopicOwnershipRecorder func(topicID string)`
   - `TopicOwnershipReceiver` extended to also require `SetTopicOwnershipRecorder(recorder TopicOwnershipRecorder)`.
5. **`core/topic_seat_binding.go`** (new file) — `topicSeatBindingStore`, a minimal JSON-file store (`topic_seat_bindings.json`) keyed by `ThreadID -> Seat`, **first-writer-wins** (a Topic has exactly one creator; unlike `topicLetterBindingStore.bind`, this must never let a later call reassign ownership). Deliberately kept separate from `dispatchStore` (whose `DispatchExpectation` shape requires Letter/Path/ResultPath fields that don't apply to an ad hoc, non-letter Topic) and from `topicLetterBindingStore` (a different concern: `{{LETTER_ID}}` workspace-pattern resolution, which is *allowed* to move over time) — same separation-of-concerns reasoning that file's own doc comment already documents for its sibling store.
6. **`core/engine.go`**:
   - `Engine.isTopicBoundToSeat` now checks the dispatch ledger **first**, then falls back to `e.ensureTopicSeatBindingStore().seatFor(topicID) == e.name`.
   - New `Engine.recordTopicBoundToSeat(topicID string)` implements `TopicOwnershipRecorder`, binding `topicID` to `e.name`.
   - `Engine.Start()` now injects both `SetTopicOwnershipChecker` and `SetTopicOwnershipRecorder`.
7. **`platform/telegram/telegram.go`**:
   - `Platform.topicOwnershipRecorder core.TopicOwnershipRecorder` field + `SetTopicOwnershipRecorder` setter.
   - `handleGeneralTopicIntake` calls `p.topicOwnershipRecorder(strconv.Itoa(topic.MessageThreadID))` immediately after `CreateForumTopic` succeeds, before any message is sent into the new Topic.

## Why this doesn't reopen L-0658 / L-0666 / L-0667

- **Sensors never actuate (L-0658):** the checker only *reads* its two sources; it writes nothing, dispatches nothing, and is consulted purely inside the existing routing decision (`isDirectedAtBot`'s return value), not a new actuation path. The *recorder* is the one write introduced by the follow-up, and it writes exactly one fact (this Topic's creating seat) at the one moment that fact is already known with certainty — it does not decide routing, dispatch anything, or re-derive anything from later messages.
- **No text/reply heuristic revived (L-0666):** the new fallback fires only after msg.Text-based command/mention checks and the (already-fixed) reply-to-bot check have all failed to match. It queries a durable key (`TopicID` → ledger `To`, or `TopicID` → binding-store `Seat`), never `msg.Text` or `msg.ReplyToMessage` on any message *after* the Topic-creating one.
- **No `[DISPATCH]` auto-execute regression (L-0667):** nothing here parses or executes a `[DISPATCH]` block; the ledger is only read, and only after a letter's dispatch already went through the Outbox confirm-card path that populates it.
- **Cardinal Invariant respected:** ownership is keyed on `TopicID` (a stable Telegram-assigned key), recorded once at dispatch time (ledger) or Topic-creation time (binding store) — never re-derived from any single message's content on every later message.

- **Deploy is not yet live**: this is a worktree with two commits (`f425acec`, `de1465fb` on `letter/L-0669`), not merged to `main` or restarted into any running seat binary. Per L-0666's own Open Points precedent, Boss should confirm in a real Topic (after merge + restart) that: (a) a `[DISPATCH]`-created Topic's bound seat now receives bare follow-up text, (b) a Topic created via General-topic `@mention` also now receives bare follow-up text without repeating the mention, and (c) an unrelated seat's bot in either kind of Topic stays silent — before treating the symptom as closed.
- **First-writer-wins is untested against real concurrent creation**: `topicSeatBindingStore.bind` assumes a Topic has exactly one creator, which holds structurally (Telegram assigns one `MessageThreadID` per `CreateForumTopic` call, and only the mentioned bot's own engine calls it) — but this has not been observed against a live multi-bot group where two different seats' usernames are both mentioned in the same General message (each would create its *own* separate Topic via its own bot token, so no actual collision is expected — flagging as an unverified structural assumption, not a known bug).
- **Scope boundary honored**: `platform/matrix/matrix.go` has its own `isDirectedAtBot` with no forum-Topic concept in Matrix's protocol; left untouched per this QUERY's Telegram-only scope. If a future letter needs the equivalent for a Matrix-style threaded platform, the same `TopicOwnershipReceiver` interface is already generic enough to reuse without further core changes.
