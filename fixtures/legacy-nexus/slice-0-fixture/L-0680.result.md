## Conclusion

根因不是"cc-connect 大小写过敏"孤例，而是**同一条派工管道里有两个对 header 大小写口径不一致的解析器**：Archive 的 PowerShell 工具（`archive-daily.ps1:21,27`）用 `-match` **大小写不敏感**，欣然接受了小写 `id:` 并给 L-0679 写了合法 INDEX 行；cc-connect 的 `parseArchiveFrontMatter`（`dispatch.go:334`）建的是**大小写敏感** map，`headers["ID"]` 取不到 `id:` → `ID=""` → 在 `dispatch.go:298` 假性拒绝。修复已落在 cc-connect 一侧（把两个解析器口径对齐 + 补齐拒绝路径的日志与审计），**责任归属判定为系统侧为主、秘书侧为辅**——理由见下。已在 worktree 提交，未 push（等 Boss/Secretary 批准）。

## Options for Boss

1. **[推荐] 采纳 cc-connect 修复，秘书侧只加轻量约定，不加机械自检**（本信已实现代码侧）
   - 代价：需 Boss/Secretary 批准 push + 开 PR + 重启才生效（merge≠deploy，见下）。
   - 收益：从根上消除触发器——任何大小写的 `id:`/`ID:`/`Id:` 都不再假性拒绝；同一修复顺带补掉 outbox 扫描器（`outbox.go:192`）和 notify header 读取的同构潜伏 bug；拒绝路径不再取证静默。秘书侧不引入脆弱的"逐信正则自检"负担。
2. **两侧都硬化**：额外在 Secretary 人设里加"落盘后 header 正则自检"强制步骤。
   - 代价：给每封信的写入流程加一道人工/LLM 自检点，增加 token 与出错面；正则本身也可能写错，形成"检查器需要被检查"的回归。
   - 收益：多一层纵深防御。**但我判定收益低于代价**——见责任归属。
3. **只改 cc-connect 告警、不改解析器容错**：仅补日志+审计，仍要求秘书写大写。
   - 代价：触发器仍在，下一次手滑还会假性拒绝，只是这次能从日志看到。不治本。

## 责任归属裁决（Expected Output item 3）

- **系统侧为主（必做，已做）**：一个协议管道内两个解析器对 header 口径不一致，是**结构缺陷**，不是使用者的错。稳健系统应对 header key 大小写不敏感（YAML/HTTP header 行业惯例皆如此），且 Archive 工具已经这么做了——cc-connect 是管道里唯一大小写敏感的一环，理应对齐，而不是反过来要求人类记住一个隐性契约。这是 L-0658/L-0662 "让派工决策可观测、可审计"方向的直接延伸。
- **秘书侧为辅（建议轻量约定，不建议机械自检）**：协议本就规定 header 大写（`bse-protocol-spec.md` §Letter Header Protocol），秘书应遵守；但**用"写后逐信正则自检"来兜底一个本应由系统容错的问题，是把系统鲁棒性缺陷转嫁成人工纪律负担**——正则自检自身会成为新的脆弱点（L-0134 侧写：narrow scope, not widen）。因此我建议秘书侧仅保留"header 用大写"的既有约定，不新增机械自检步骤。是否仍要加，属于 Boss 对纵深防御偏好的取舍，我不替 Boss 选定（列为 Option 2）。

## Observations & Invariants at Risk（承重改动前置）

- **观察（一手证据）**：
  - `dispatch.go:298` `if headers["ID"] != req.Letter` + `dispatch.go:334` `headers[strings.TrimSpace(key)]=…`（无大小写归一）→ 大小写敏感取值，此为触发点。
  - `archive-daily.ps1:21,27` `$_ -match "^$([regex]::Escape($Key)):\s*(.+)$"` → PowerShell `-match` 默认大小写不敏感，故 INDEX 侧接受了小写 `id:`。两解析器口径分歧被证实。
  - **取证静默已证实**：`grep -i "Dispatch rejected\|does not match" F:\nexus\logs\cc-connect-stdout.log` → **零命中**；日志里只见 L-0679 修好后于 `16:08:41` 成功建 worktree/spawn。拒绝路径（`dispatch.go` 原 536/539/557 行）返回了 `⚠️` 字符串却从不 `slog`、也从不进 L-0662 审计账本（`recordControlPlaneDispatch` 只在 `ControlPlaneDispatch` 内部跑，pre-validation 拒绝根本到不了那里）。这印证了 QUERY "静默吞没" 的核心担忧——但需修正 QUERY 的一处表述：代码**确实**向前台返回了 `⚠️ Dispatch rejected` 文本（`engine.go:6236-6238` 把 replacement 赋给出站文本），并非"完全无任何前台反馈"；真正的缺口是**日志/审计层**的取证静默，以及 `/outbox` 因未入账而无卡片（Finding #2 属实）。
  - `dispatch.go:319` 的 `parseArchiveFrontMatter` 有 4 个调用方（`dispatch.go:297/350`、`notify.go:947`、`outbox.go:191`），全部按大写 key 取值——故在解析器一处归一即修复全部，无需改 4 处调用点（不造轮子）。
- **风险不变量**：本改动不触碰持久身份派生——派工目标仍由 `[DISPATCH]` 块的 `To:`/`Path:`（稳定键）驱动，header 大小写归一只影响**校验通过与否**，不改变任何 session/workspace/shard/resume 的身份来源。Cardinal Invariant 未受影响。
- **部署真相**：已验证的是**源码编译 + `go test ./core` 全绿（31.3s）+ `go vet` 干净**；**尚未** rebuild 生产 binary、**尚未**重启。merge≠deploy——修复要进运行舰队，需 Boss/Secretary 批准 push→PR→合并→重启后才生效。当前运行 binary 仍是旧逻辑。
